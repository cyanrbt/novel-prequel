# 小说质量进化管线设计

## 1. 背景

当前系统已经具备三 Agent 分工、单一叙事状态、受控上下文、静态与语义双门禁、失败隔离和原子提升。现有流程一次生成一份正文，由单个 Reviewer 给出综合判断；它擅长防止设定和状态错误，但对以下长篇问题缺少系统性处理：

- 单章只有一个候选，无法通过比较发现“合格但不够好”的稿件；
- 同一个综合 Reviewer 同时判断连续性、人物、文学性和 AI 痕迹，容易遗漏专项问题；
- 最近上下文以五章摘要和硬编码人物声纹为主，难以支撑 600 章的长期检索；
- 审查发现的问题不会沉淀为可遗忘、可验证的后续经验；
- 缺少十章、二十章尺度的节奏、人物和伏笔复审；
- 通过门禁的稿件只有 PASS/REVISE 结论，没有带置信度的自动提升政策。

本设计借鉴以下项目的方法，但只吸收适合当前 Python CLI 管线的核心能力：

- [NousResearch/autonovel](https://github.com/NousResearch/autonovel)：候选比较、专项修订、读者面板和分数平台期停止；
- [Ckokoski/AuthorAgent](https://github.com/Ckokoski/AuthorAgent)：角色审稿、分层记忆、专项修订和经验学习；
- [alfredxw/denova](https://github.com/alfredxw/denova)：渐进式上下文、可追踪修改和本地恢复。

本轮不建设网页 IDE、出版套件、封面、有声书、营销或互动故事模式。

## 2. 目标与成功标准

### 2.1 目标

在保留现有 Python CLI、正式状态和原子提升边界的前提下，将单稿审查升级为可审计的质量进化管线：

1. 每章由同一份核准规划生成三个有明确差异的候选稿；
2. 使用连续性、人物、文学性和反 AI 痕迹四类专项审查；
3. 通过确定性门禁、加权评分和盲选多数票选择优胜稿；
4. 对共识问题最多执行两轮定向修订，只保留可测量的改进；
5. 高置信度结果自动提升，边界结果等待人工确认；
6. 建立有界长期记忆、可遗忘质量经验和十章/二十章阶段复审；
7. 所有模型调用、证据、得分、淘汰和提升决定均可恢复、可解释、可测试。

### 2.2 成功标准

- 没有候选可以绕过现有 P1 静态门禁或新的连续性硬门禁；
- 自动提升的每项条件都有结构化工件和正文证据；
- 正式 `current.json` 只在原子提升时改变；
- 运行中断后可以从最后一个有效阶段恢复，不重复已完成调用；
- 每次写作最多向 Writer 注入八条相关质量经验；
- 阶段复审只产生创作债务和未来约束，不自动改写历史正文；
- 旧配置可以通过默认模型路由继续运行；
- 全部自动测试通过，并能完成第 3 章的完整 dry-run。

## 3. 非目标

- 不允许 Agent 直接修改正式章节、正式元数据或正式状态；
- 不为第一版引入向量数据库、外部搜索服务或云端记忆；
- 不自动重写已经提升的历史章节；
- 不追求零缺陷或无限修订；单章修订最多两轮，章节重试沿用现有上限；
- 不把模型分数当成事实；硬规则和证据验证始终优先于综合分；
- 不要求配置多个模型提供方，默认可全部复用 Codex CLI。

## 4. 总体架构

现有 `WritingPipeline` 继续作为唯一编排入口。新增组件均通过明确的结构化接口工作，不拥有正式文件写入权限。

```text
Planner
  ↓ 一份核准规划
Candidate Producer
  ↓ 三个差异化候选
Static Gate
  ↓ 硬门禁合格候选
Specialist Review Panel
  ↓ 四类评分、问题与证据
Candidate Selector
  ↓ 确定性评分 + 三次盲选
Revision Controller
  ↓ 最多两轮定向修订与回归检查
Promotion Policy
  ├─ 高置信度：原子提升
  └─ 边界结果：WAITING_USER 工作区状态
Memory/Audit Updater
  ↓ 索引、质量经验和阶段复审债务
```

### 4.1 Model Router

Model Router 根据阶段名称解析模型档案。支持规划、候选写作、四类专项审查、比较裁决、定向修订和阶段复审分别配置模型。若阶段没有显式路由，则回退到 `default`；若新配置不存在，则回退到现有 `provider` 配置。

路由器只负责选择并构造 `ModelProvider`，不解析业务输出、不决定得分。

### 4.2 Candidate Producer

Candidate Producer 对一份已通过规划校验的 `plan.json` 生成三个候选。三个候选共享全部事实、连续性和禁入约束，但分别得到一个创作侧重点：

1. `character_conflict`：优先强化人物目标冲突、关系变化和对白差异；
2. `horror_evidence`：优先强化可观察异常、试错链和现实代价；
3. `pacing_compression`：优先减少解释与重复，使场景进入和退出更锋利。

侧重点只能改变信息呈现和场景重心，不能改变核准规划、增加关键解法或移除不可逆变化。若某候选生成失败，其他候选继续；有效候选少于两个时补生成，直至达到重试上限。

### 4.3 Specialist Review Panel

四个专项 Reviewer 分别输出独立 JSON：

- `continuity`：时间、地点、人物知识边界、能力闸门、事实等级、异常规律、伏笔和规划兑现；
- `character`：动机、利益、关系变化、声纹、行为可信度和角色工具化；
- `craft`：场景张力、节奏、信息呈现、情绪落点、结构重复和章末因果；
- `anti_slop`：解释过度、同义复述、固定动作、句式模板、开头/结尾模板和跨章机械重复。

每份审查必须提供 0–100 分、问题严重度、正文精确引文、判断说明和可验证修订要求。审查证据必须原样存在于候选正文；无效证据会使该审查工件失效并仅重跑该 Reviewer。

Reviewer 只诊断，不直接修改候选稿。

### 4.4 Candidate Selector

Selector 分两步工作：

1. 确定性选择器根据硬门禁、资格线和加权分淘汰不合格候选；
2. 独立裁决模型对合格稿进行去编号、随机前后顺序的成对比较。三个合格候选采用三组两两循环赛；只有两个合格候选时，将同一组比较以交换顺序的方式执行三次。

盲选只比较同一规划下的兑现程度、人物可信度、节奏与信息密度、解释和模板数量。至少获得两票的候选才能成为优胜稿。循环赛中没有候选获得两票，或盲选结果与专项加权分第一名冲突时，结果自动降为低置信度并等待人工确认。

### 4.5 Revision Controller

Revision Controller 汇总多个 Reviewer 对优胜稿的共识问题，生成限定范围的修订简报。简报明确：

- 必须修复的问题及原文证据；
- 必须保留的场景、信息和有效段落；
- 不得改变的规划、设定和人物认知；
- 修订验收条件。

每章最多两轮修订。每轮修订后重新执行静态检查和四类专项审查，并让裁决模型以交换顺序的三张选票比较修订稿与上一版本。加权总分没有提高、任一维度下降超过 3 分，或修订稿没有获得至少 2/3 盲选支持时，丢弃本轮修订并保留上一版本。

### 4.6 Promotion Policy

Promotion Policy 是纯确定性组件，只消费已经验证的得分、选票和问题状态。它不调用模型，也不修改正文。

高置信度自动提升必须同时满足：

- 所有静态和语义硬门禁通过；
- 修订后加权总分不低于 85；
- 连续性不低于 90；
- 人物、文学性、反 AI 痕迹均不低于 82；
- 盲选至少获得 2/3 支持；
- 专项加权分第一名与盲选优胜稿一致；
- 没有未解决的必须修订项；
- 修订没有造成任何维度下降超过 3 分。

以下情况进入人工确认：

- 总分为 78–84；
- 盲选平票或重裁后仍冲突；
- 加权分第一名与盲选优胜稿不同；
- 两轮修订仍没有达到自动提升线；
- 审查者对同一问题给出互相排斥的必须修订要求。

总分低于 78 或没有候选通过资格线时重新规划，受现有 `max_retries` 限制。

## 5. 评分模型

候选必须先通过所有硬门禁，再进入评分。加权分不能抵消硬门禁失败。

| 维度 | 权重 | 候选资格线 |
|---|---:|---:|
| 连续性与设定 | 30% | 85 |
| 人物与关系 | 25% | 75 |
| 文学性与节奏 | 30% | 75 |
| 反 AI 痕迹 | 15% | 80 |

候选加权总分计算公式为：

```text
continuity × 0.30
+ character × 0.25
+ craft × 0.30
+ anti_slop × 0.15
```

硬门禁包括：

- 现有静态 P1 检查失败；
- 正传事实、年代、能力或人物知识边界冲突；
- 规划核心不可逆变化没有兑现；
- 新角色、新异常、新物品或新规则未经规划批准却承担关键解法；
- 任何必须存在的审查证据无法在正文中定位；
- 候选与近期正式章节或其他候选存在明显大段复用。

阈值均保存在配置中。初始值通过第 1、2 章只读基线审查校准，但校准不得降低 P1 标准。

## 6. 长期记忆

### 6.1 CORE

CORE 是每次调用都可见的有界记忆，包括：

- 当前状态与本章规划；
- 本章涉及的人物、地点、异常和物品；
- 相关能力闸门、活跃伏笔和关系变化；
- 当前事件结构目标与未解决创作债务；
- 与本阶段相关的最多八条质量经验。

不同阶段获得不同 CORE 视图。Writer 不接收无关审查历史；专项 Reviewer 不接收其他 Reviewer 的结论；Selector 不接收候选编号和生成模型信息。

### 6.2 ARCHIVAL

每章正式提升后建立结构化索引，记录来源章号和正式工件哈希：

- 人物出场、已知信息和关系变化；
- 地点、物品、异常规律和证据；
- 伏笔播种、推进、回收与当前年龄；
- 场景类型、开头方式和结尾钩子；
- 章节摘要、不可逆变化和审查等级。

第一版使用稳定 ID、人物、地点、事件和伏笔进行确定性关联检索。只有 Planner 或连续性 Reviewer 需要核对早期事实时，才读取对应正式章节片段。

### 6.3 RECALL

正式章节、章节元数据和 `current.json` 是不可替代的真源。ARCHIVAL 只是派生索引。索引中的来源哈希与正式文件不一致时，索引失效并从正式工件重建。

### 6.4 质量经验生命周期

同类问题在最近十章至少出现三次才升级为活跃经验。每条经验包含：

- 稳定问题代码；
- 适用角色、场景或全书范围；
- 首次和最近出现章号；
- 至少三条来源证据；
- 给 Writer 或 Planner 的可执行约束；
- 当前状态：`candidate`、`active` 或 `retired`。

Writer 每次最多接收八条与本章相关的活跃经验。某条经验连续十章未复发时转为 `retired`，不再默认进入上下文；再次达到复发条件时可以重新激活。质量经验不能改变设定事实、人物状态或能力闸门。

## 7. 阶段复审

### 7.1 十章健康检查

每完成十章自动生成一次只读健康报告，检查：

- 场景类型和调查推进结构是否重复；
- 人物出场、关系变化和主动选择分布；
- 开头方式、结尾钩子和固定动作分布；
- 伏笔年龄、长期未推进项和过密回收；
- 近期语言模板、解释过度和重复意象。

报告产生带优先级、来源和验收条件的创作债务，供后续 Planner 使用。

### 7.2 二十章阶段复审

每完成二十章自动评估：

- 当前事件弧相对大纲的进度；
- 揭示速度和规则认知层级；
- 人物厚度、关系弧和长期缺席角色；
- 节奏曲线、连续同构章节和缺失的缓冲场景；
- 已承诺但尚未兑现的伏笔和代价。

阶段复审只更新派生的创作债务和未来规划约束。它不得修改历史正式章节、正式元数据或正式状态。修改旧章节必须由用户另行明确发起。

## 8. 模型配置

配置新增命名模型档案与阶段路由。默认所有档案均可指向现有 Codex CLI。

```json
{
  "model_profiles": {
    "default": {"type": "codex_cli"},
    "prose": {"type": "codex_cli"},
    "judge": {"type": "codex_cli"}
  },
  "stage_routes": {
    "planner": "default",
    "candidate_writer": "prose",
    "continuity_reviewer": "judge",
    "character_reviewer": "judge",
    "craft_reviewer": "judge",
    "anti_slop_reviewer": "judge",
    "selector": "judge",
    "reviser": "prose",
    "arc_reviewer": "judge"
  }
}
```

配置优先级为：阶段显式路由、`default` 模型档案、旧 `provider` 配置。模型档案沿用现有 provider 安全边界，Agent 仍以只读沙箱运行。

`run_manifest.json` 记录：

- 当前阶段和完成状态；
- 规划、上下文、候选和审查工件哈希；
- 使用的模型档案和提示词版本；
- 每阶段调用次数、失败原因和重试次数；
- 当前推荐候选、置信度与等待原因。

所有 JSON 工件采用原子写入。`next --resume` 校验结构和哈希后，从第一个缺失或失效阶段继续。已经完成且输入未变化的调用不得重复执行。

局部失败策略：

- 候选生成失败只影响该候选；有效候选少于两个时补生成；
- 单项审查失败只重跑该 Reviewer；
- 首轮盲选无法形成多数时重新随机排序裁决一次，仍冲突则等待人工；
- 修订没有提高时回退上一版本；
- 所有候选不合格时重新规划；
- 达到最大尝试次数后停止，正式文件保持不变。

正式状态的逻辑等待状态由 `run_manifest.json` 表达。`current.json` 不为了显示 `WAITING_USER` 单独写入；CLI `status` 从当前有效运行中派生显示等待原因。

## 10. 自动提升安全

自动或人工提升前必须重新验证：

- 当前正式状态哈希与生成时一致；
- `next_chapter` 与规划章号一致；
- 正式目标章节尚不存在；
- 最终正文、规划、全部审查、选票和决策哈希一致；
- 最终正文重新通过静态检查和审查结构验证；
- 对自动提升而言，所有自动提升阈值仍满足；
- 对人工候选选择而言，该候选至少通过全部硬门禁。

验证后沿用现有章节正文、章节元数据和正式状态三文件原子提升。任一步骤失败均回滚，不允许留下半完成正式状态。

## 11. CLI 行为

- `next`：运行完整候选管线；高置信度自动提升，边界结果保留在工作区；
- `next --dry-run`：完成全部质量流程但不自动提升；
- `next --resume`：恢复最近一次输入仍有效的未完成运行；
- `status`：显示当前章节、运行阶段、有效候选数和等待原因；
- `accept`：接受系统推荐的边界稿，提升前重新校验；
- `accept --candidate 2`：选择另一个通过硬门禁的候选并重新执行最终审查；
- `review --last 10`：审查近期章节并在满足间隔时生成健康报告；
- `audit --arc`：手动触发二十章级阶段复审，不修改正式章节。

每次运行生成 `decision.md`，展示候选淘汰原因、四项得分、盲选结果、修订前后变化、自动提升或等待条件，以及质量经验变化。JSON 工件是程序真源，Markdown 只用于人工阅读。

## 12. 错误处理

- 模型输出不是合法结构化工件：仅重试当前阶段，并保留原始错误摘要；
- 审查引文不在正文：该审查失效，仅重跑该 Reviewer；
- 模型路由缺失或档案无效：预检失败，不开始章节生成；
- 工作区哈希不一致：停止恢复并报告首个不一致工件；
- 正式状态在运行期间变化：拒绝提升，要求以新状态重新运行；
- 派生记忆与正式来源哈希不一致：忽略派生记录并重建，不阻止读取正式真源；
- 阶段复审失败：记录审计失败但不回滚已经安全提升的章节；下次命令可以单独恢复审计；
- 决策冲突或证据不足：不得自动提升，进入人工确认。

## 13. 测试策略

### 13.1 单元测试

覆盖：

- 阶段模型路由与旧配置回退；
- 资格线、权重和自动提升政策；
- 盲选多数票和冲突处理；
- 修订退步检测与版本回退；
- 嵌套工件路径安全、结构和哈希验证；
- CORE 预算、ARCHIVAL 关联检索和来源失效；
- 质量经验升级、降级、重新激活和八条上限；
- 十章/二十章触发规则。

### 13.2 管线集成测试

使用可编程假模型验证：

- 三候选正常择优并自动提升；
- 部分候选失败后补生成；
- 单项审查失败只重跑该项；
- 全部候选不合格后重新规划；
- 盲选与加权分冲突后等待人工；
- 修订提高时采用新稿，退步时保留上一稿；
- 中断恢复不重复完成的调用；
- 正式状态变化后拒绝恢复或提升；
- 原子提升失败后正文、元数据和状态全部回滚。

### 13.3 回归测试

保留并扩展现有预检、状态校验、重复检测、dry-run、`accept`、恢复和原子提升测试。旧 `provider` 配置必须继续可用。

### 13.4 质量校准

对现有第 1、2 章执行只读专项审查，验证 Reviewer 能提供真实原文证据，并记录初始得分、模型调用数和耗时。评分存在模型波动，因此自动测试验证结构、证据和政策，不断言真实模型的固定文学分数。

## 14. 实施顺序约束

实施按以下依赖顺序展开：

1. 配置、模型路由和结构化工件协议；
2. 候选生成、专项审查和确定性评分；
3. 盲选、定向修订和提升政策；
4. 可恢复运行和 CLI；
5. 分层记忆、质量经验和阶段复审；
6. 文档、基线校准和完整 dry-run。

每一阶段必须保持现有正式提升安全边界，并以自动测试证明可回滚、可恢复后再进入下一阶段。
